FreeRTOS

信号量（Semaphore）

信号量是 FreeRTOS 中用于任务间同步与通信的核心机制。可以把信号量理解为一个计数器，配有两个原子操作：

  • Take（拿/Pend）：计数器减 1。如果计数器已经是 0，任务就阻塞等待。
  • Give（给/Post）：计数器加 1。如果有任务正在等，就唤醒它。

三种类型及用途

类型 计数器范围 典型场景
二值信号量 0 或 1 任务同步，事件通知
计数信号量 0 ~ N 资源管理，累计事件
互斥锁（Mutex） 0 或 1 保护共享资源（带优先级继承）

常见使用场景

1. 任务间同步（二值信号量）

1
2

任务A：采集完传感器数据 → Give信号量
任务B：Take信号量（一直阻塞等待）→ 被唤醒 → 处理数据

就像"闹钟"：任务 B 睡觉等信号，任务 A 数据准备好了就"响铃"叫醒 B。

2. 资源管理（计数信号量）

假设系统只有 3 个 UART 发送缓冲区，最多同时 3 个任务使用：

1
2
3
4
5
6

SemaphoreHandle_t uartSem = xSemaphoreCreateCounting(3, 3);  // 初始3个可用

// 每个任务用之前：
xSemaphoreTake(uartSem, portMAX_DELAY);   // 拿一个，剩余2
// ... 使用UART ...
xSemaphoreGive(uartSem);                   // 还回去，剩余变回3

第 4 个任务再来拿时，计数器已经是 0，就会阻塞排队。这就是有限资源的分配管理。

void UART_RX_IRQHandler() {
    // 收到一个字节
    xSemaphoreGiveFromISR(uartRxSem, &woken);  // 在中断中Give

// 数据处理任务里：

    xSemaphoreTake(uartRxSem, portMAX_DELAY);  // 等数据到来
    processByte();
}

让硬件中断与用户任务解耦，中断只负责"通知"，处理逻辑在任务里做。

和互斥锁的区别

信号量 互斥锁
谁拿谁还 可以任务 A 拿、任务 B 还 必须同一个任务拿和还
优先级继承 没有 有（防止优先级反转）
用途定位 同步/通知 保护共享资源
比喻 红绿灯（信号来了就走） 厕所门锁（谁进谁出）

简单记住：信号量用于"通知"，互斥锁用于"保护"。

互斥锁（Mutex）

互斥锁是一个只有两把钥匙的锁：锁只有两种状态——“锁着"和"开着”。操作系统保证两点：

  1. 任何时刻，最多只有一个任务能拿到锁。
  2. 只有拿锁的任务才能还锁。

为什么需要它——数据竞争问题

假设两个任务都要对全局变量 g_counter++ 操作：

1
2
3
4
5
6

int g_counter = 0;

// 任务A                           // 任务B
LOAD  R0, [g_counter]   // R0=0    LOAD  R0, [g_counter]   // R0=0
ADD   R0, #1            // R0=1    ADD   R0, #1            // R0=1
STORE R0, [g_counter]   // c=1     STORE R0, [g_counter]   // c=1

g_counter++ 在汇编层面是三条指令，不是原子的。任务 A 算到一半，任务 B 抢占进来读到旧值 0，最终两次加一结果却是 1 而不是 2——这就是数据竞争。

加了互斥锁之后：

1
2
3

任务A拿锁 → LOAD→ADD→STORE → 还锁
                                ↓
                           任务B拿锁 → LOAD→ADD→STORE → 还锁

临界区变成串行执行，g_counter 正确变成 2。

FreeRTOS 中的常用 API 

1
2
3
4
5

SemaphoreHandle_t mutex = xSemaphoreCreateMutex();   // 创建（初始值为 1，开锁状态）

xSemaphoreTake(mutex, timeout);    // 拿锁。拿不到就阻塞，直到超时或拿到
xSemaphoreGive(mutex);             // 还锁。唤醒等待队列中的下一个任务
vSemaphoreDelete(mutex);           // 删除

你代码里 portMAX_DELAY 就是超时时间设为"永远等"，拿不到锁就死等，绝不放弃。

优先级反转与优先级继承

这是互斥锁和普通信号量最关键的区别。

问题场景：

1
2
3
4
5
6

优先级：任务H(高) > 任务M(中) > 任务L(低)

1. 任务L 拿了锁，正在忙
2. 任务H 抢占了 L，也想拿锁 → 阻塞等待 L 还锁
3. 任务M 抢占了 L（M 优先级比 L 高），L 根本没机会执行
结果：任务H 被优先级不如它的任务M 无限期阻塞 → "优先级反转"

FreeRTOS 互斥锁的解决方案——优先级继承：

当任务 H 等待任务 L 持有的锁时，FreeRTOS 临时把任务 L 的优先级提升到和任务 H 一样高。这样任务 M 无法抢占 L，L 能快速执行完临界区、还锁，H 立刻拿到锁继续运行。

使用注意事项

规则 为什么
临界区尽量短 别人都在排队等你
不要在临界区里阻塞（delay、等信号量） 死锁风险，别人永远拿不到
拿锁和还锁必须成对出现 忘了还就是死锁
不要嵌套拿多个锁 A 等 B，B 等 A → 死锁
中断里不能用 xSemaphoreTake 中断不能阻塞，会导致崩溃

一句话总结

互斥锁 = 保证"一段代码"同时只有一个人能跑，是防止多任务互相踩踏数据的最常用手段。它的特殊之处在于带优先级继承，这是普通信号量做不到的。
